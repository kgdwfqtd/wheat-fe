二、P0 严重问题（需立即修复）

P0-1upsert_record() INSERT 分支列拼接 Bug

位置：database.py 第 220 行

# 当前代码（有 Bug）
all_cols = (["plot_id"] + list(extra_keys.keys()) if extra_keys else ["plot_id"]) + list(data_dict.keys())
# 当 extra_keys 存在时，运算优先级导致：
# (["plot_id"] + list(extra_keys.keys())) + list(data_dict.keys())  ← 正确
# 当 extra_keys 为 None 时：
# (["plot_id"]) + list(data_dict.keys())  ← 也正确
# 但如果 extra_keys 是空 dict {} (falsy)，则走 else 分支，丢失 extra_keys 列

风险：当 extra_keys={} 传入时，复合键列丢失，INSERT 缺少 phase 列导致报错或数据不一致。

修复：加括号明确优先级：all_cols = ["plot_id"] + (list(extra_keys.keys()) if extra_keys else []) + list(data_dict.keys())

P0-201_plots.py 直接执行 DELETE 绕过白名单

位置：pages/01_plots.py 第 75-79 行

with get_conn() as conn:
    tables = ["operation_log", "quality_data", "yield_data", ...]
    for t in tables:
        conn.execute(f"DELETE FROM {t}")  # 直接 f-string，未走 _check_table()

风险：虽然表名列表是硬编码的，但这破坏了 _check_table() 的安全防线，形成了不一致的安全实践。如果后续有人复制此模式，可能引入注入风险。

修复：在 database.py 中提供 reset_all_data() 函数，内部使用白名单校验，页面只调用该函数。

P0-3backup_db() 覆盖式备份 — 只保留一个备份

位置：database.py 第 408-412 行

def backup_db():
    bak_path = DB_PATH + ".bak"  # 固定文件名，每次覆盖
    shutil.copy2(DB_PATH, bak_path)
    return bak_path

风险：每次备份都覆盖上一次的 .bak 文件。如果用户连续操作后发现数据错误，只能回退到最近一次备份，之前的备份全部丢失。对于科研数据这是致命的。

修复：备份文件名加时间戳：bak_path = DB_PATH + f".{datetime.now().strftime('%Y%m%d_%H%M%S')}.bak"，并保留最近 N 个备份。

P0-4utils.py fe_total 类型不一致 — str 与 float 混用

位置：utils.py 第 8-13 行

TREATMENTS = [
    {"code": "CK",     "fe_total": 0},           # int
    {"code": "FS",     "fe_total": "2.0 kg/亩"},  # str ← 不一致！
    {"code": "NF-0.5", "fe_total": 0.5},          # float
    ...
]

风险：get_nf_plot_dose() 中用 isinstance(total, (int, float)) 判断，FS 处理返回 0 而非正确值。虽然 FS 不是纳米铁处理不影响主逻辑，但类型不一致是隐患，容易在后续扩展时引发 Bug。

修复：统一为 "fe_total": 2.0（float），单位单独放 "fe_unit": "kg/亩" 字段。

三、P1 中等问题（建议尽快修复）

P1-1无异常处理 — 数据库操作裸奔

upsert_record()、add_operation() 等函数没有 try/except，数据库锁定、磁盘满等异常会直接抛到 Streamlit 页面，用户看到的是 Streamlit 的红色错误栈，而非友好的错误提示。

建议：在 Service 层统一捕获 sqlite3.Error，返回 (success: bool, message: str) 元组，页面层根据结果展示 st.success() 或 st.error()。

P1-2get_treatment_table_matrix() 仍是 N+1 查询

注释写着"修复 N+1 连接风暴"，但实际仍然是循环 6 个处理 × 7 个表 = 42 次查询，加上 soil_data 的查询共 48 次。虽然比逐小区查询好，但仍可优化。

建议：使用一条 SQL 完成全部统计：

SELECT p.treatment,
       COUNT(DISTINCT CASE WHEN t.plot_id IS NOT NULL THEN t.plot_id END) as cnt
FROM plots p
LEFT JOIN soil_data t ON p.id = t.plot_id
GROUP BY p.treatment

对每个表做一次 LEFT JOIN 统计，总共 7 条 SQL 即可（从 48 降至 7）。

P1-3无 Service 层 — 业务逻辑散落在页面中

产量计算逻辑在 06_yield.py、出苗率计算在 03_phenology.py、纳米铁用量计算在 08_operations.py。这些逻辑无法被复用、无法被测试，如果需要在导出页面展示计算结果就得复制一遍。

建议：抽取 services/ 目录，按领域拆分 Service 模块。

P1-4form_helper 未被所有页面使用 — 代码重复

02_soil.py、03_phenology.py、06_yield.py 手写了表单逻辑，与 form_helper.render_data_entry_page() 高度重复。这些页面有特殊逻辑（复合键、Tab、自动计算），但可以扩展 form_helper 支持这些场景。

建议：form_helper 增加 on_submit 回调参数，让页面可以注入自定义计算/校验逻辑。

P1-5无数据校验规则集中管理

每个页面的校验逻辑都是临时写的（出苗数 > 播种粒数、千粒重差异 > 5%），没有统一的校验规则定义。校验器 validators 参数在 form_helper 中定义了但实际从未使用。

建议：创建 validation.py，定义各字段的校验规则（范围、逻辑关系），form_helper 自动应用。

P1-6无配置文件 — 路径和常量硬编码

DB_PATH 硬编码为脚本同目录，PLOT_RATIO = 0.03 硬编码，小区面积 20.0 硬编码在 DDL 中。如果试验方案变更（小区面积改变、处理数增减），需要改多处代码。

建议：创建 config.py，集中管理所有可配置参数，支持环境变量覆盖。

P1-7无数据库迁移机制

init_db() 使用 CREATE TABLE IF NOT EXISTS，如果表结构需要变更（新增列、修改约束），无法自动迁移。现有数据会阻止修改。

建议：引入简单的版本号迁移机制：在 DB 中建 schema_version 表，每次启动检查版本号，依次执行迁移脚本。

P1-8无日志记录 — 操作不可追溯

系统有"操作日志"功能记录试验操作，但程序自身的运行日志（谁在什么时候保存了什么数据、是否出错）完全没有记录。如果数据出现异常，无法追溯。

建议：使用 Python logging 模块，在 Service 层记录关键操作（save/update/delete）和异常。

P1-9无数据分页 — 大数据量时性能问题

get_all_records() 和 get_operations() 一次返回全部数据。目前数据量小（18 小区），但如果扩展到更多试验或多年度数据，页面会变慢。

建议：在查询函数中增加 limit/offset 参数，页面使用 st.dataframe 的虚拟滚动。

P1-10Plotly 已声明但未使用

requirements.txt 中声明了 plotly>=5.0，但 09_export.py 中全部使用 Streamlit 内置 st.bar_chart，Plotly 从未被导入。要么移除依赖，要么用 Plotly 替换以获得更丰富的图表（误差棒、交互式图例等）。

建议：科研数据可视化建议用 Plotly，支持误差棒（标准差）、多图叠加等科研常用图表。

P1-11get_completion_stats() 中 f-string 拼接表名

位置：database.py 第 322 行

cnt = conn.execute(f"SELECT COUNT(DISTINCT plot_id) FROM {tbl}").fetchone()[0]

虽然 tbl 来自硬编码列表 tables_1to1，实际安全，但与 _check_table() 的安全实践不一致，容易误导后续开发者。

建议：在循环内调用 _check_table(tbl)，保持安全实践一致性。

四、P2 改进建议（长期优化）

P2-1无单元测试

项目完全没有测试。产量计算、出苗率计算、upsert 逻辑等核心业务逻辑应该有测试覆盖。建议使用 pytest + pytest-streamlit 或直接测试 Service 层函数。

P2-2无类型提示（部分函数）

database.py 中 init_db()、init_plots()、get_all_plots()、add_operation() 等函数缺少类型提示。form_helper.py 做得好，有完整类型标注。

P2-3无 CSV 导出选项

目前只支持 Excel 导出。科研人员常需要 CSV 格式导入 SPSS、R 等统计软件。建议增加 CSV 导出。

P2-4图表分析功能薄弱

当前只有产量、籽粒铁、SPAD 三种柱状图。建议增加：处理间差异显著性分析（ANOVA）、处理 × 区组交互图、物候期时间轴、多指标相关性矩阵等科研常用图表。

P2-5无数据导入功能

如果用户在田间用其他工具（Excel、手机备忘录）记录了数据，无法批量导入系统。建议增加 Excel/CSV 导入功能。

P2-6无用户认证

如果部署在局域网内多人使用，所有人都能修改数据，无法区分操作人。建议增加简单的密码认证或 Streamlit Authenticator。

P2-7无数据审计追踪

科研数据要求可追溯。当前 upsert 操作直接覆盖旧值，无法知道数据何时被修改、修改前是什么值。建议增加数据变更历史表。

P2-8__pycache__ 提交到项目目录

__pycache__ 目录和 .pyc 文件不应出现在项目根目录。建议添加 .gitignore。
